OSGi bundles

curie-osgi turns the project JAR into an OSGi bundle during curie build, then publishes that bundle to an OSGi Bundle Repository during curie publish. It is a lifecycle plugin - it does not generate sources.

Installation

terminal 
cargo install --path plugins/curie-osgi

The binary must be named curie-osgi and sit on PATH. Curie discovers it the same way it discovers curie-protobuf.

Activating the plugin

Curie.toml 
[library]
name    = "osgi-greeter"
version = "1.0.0"
groupId = "com.example.curie"

[plugin.osgi]
symbolicName  = "com.example.curie.osgi-greeter"
bundleName    = "OSGi Greeter"
exportPackage = "com.example.osgi"
repository    = "file:target/osgi-repo"

Configuration keys

KeyTypeDefaultNotes
symbolicNamestringgroupId.artifactIdBundle-SymbolicName
bundleVersionstringproject version, OSGi-normalized1.0.0-SNAPSHOT becomes 1.0.0.SNAPSHOT
bundleNamestring-Bundle-Name
activatorstring-Bundle-Activator
exportPackagestringevery package that contains a .classWritten as-is when set; otherwise inferred from the JAR
importPackagestring-Import-Package; omitted when unset
privatePackagestring-Comma-separated patterns excluded from inferred exports. A trailing .* is a prefix match
headerstableemptyExtra MANIFEST.MF headers, e.g. Bundle-Vendor
repositorystringrequired at publishfile: path, http(s): URL, or a [[repositories]] id

What curie build does

After the project JAR is packaged, Curie calls curie-osgi run --phase post-package. The plugin rewrites META-INF/MANIFEST.MF in place: existing headers such as Main-Class and Class-Path are kept, and the OSGi headers are merged in. Export-Package is versioned with the bundle version, Import-Package is taken from class-file type references, and Require-Capability: osgi.ee is derived from the oldest class-file version (the same clause bnd writes).

$ curie build 
Building osgi-greeter v1.0.0
  Compile          1 source file(s)
  Tests            no test sources found
  Package          osgi-greeter-1.0.0.jar
  Plugin osgi      post-package
  Done             target/osgi-greeter-1.0.0.jar

The next build skips the plugin when the JAR and [plugin.osgi] config are unchanged (stamp at target/.curie-plugins/osgi.post-package.stamp).

What curie publish does

After the Maven upload, Curie calls curie-osgi run --phase publish. The plugin writes the bundle plus an OBR repository.xml to the configured repository:

  • file:target/osgi-repo - a local dummy OBR on disk
  • http://host:port/ - HTTP PUT of bundles/<bsn>-<version>.jar and repository.xml
  • A [[repositories]] id - URL and credentials come from the project and ~/.curie/config.toml

curie publish --dry-run still invokes the plugin; the plugin prints the PUT plan and writes nothing.

Dummy HTTP repository

curie-osgi dummy-repo is a tiny PUT/GET server for local testing:

terminal 
curie-osgi dummy-repo --dir /tmp/osgi-repo --port 9999

Point [plugin.osgi] repository at http://127.0.0.1:9999 and run curie publish. The server stores whatever is PUT under --dir.

Example

examples/osgi-bundle-demo is a one-class library with the plugin enabled. After curie build, the JAR manifest includes Bundle-SymbolicName, versioned Export-Package, and Require-Capability: osgi.ee for Java 21.

Maven sync keeps <packaging>jar</packaging> and follows the Felix recipe for adding OSGi metadata without changing the packaging type: the bundle plugin's manifest goal only writes target/classes/META-INF/MANIFEST.MF; maven-jar-plugin must set <manifestFile> to that path or the packaged JAR keeps a default Archiver manifest with no OSGi headers. Maven Archiver may still add Created-By / Build-Jdk-Spec; those are not OSGi attributes.
