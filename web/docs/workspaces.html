Subsystem · workspaces

Workspaces

Curie inherits Cargo's workspace model. One root Curie.toml lists members; each member is a self-contained project; the root inherits shared config down to every member.

Layout

tree 
monorepo/
├── Curie.toml          # workspace root — no [application] / [library]
├── app/
│   ├── Curie.toml      # declares [application]
│   └── src/...
├── core/
│   ├── Curie.toml      # declares [library]
│   └── src/...
└── utils/
    ├── Curie.toml      # declares [library]
    └── src/...

Root configuration

The root Curie.toml declares members and any config that should be inherited:

Curie.toml — workspace root 
[workspace]
members = ["app", "core", "utils"]

[java]
releaseVersion = "21"

[bom-imports]
"com.fasterxml.jackson:jackson-bom" = "2.17.2"

[test-bom-imports]
"org.junit:junit-bom" = "5.11.0"

Inheritance rules

  • [java] — applies to every member that does not declare its own.
  • [bom-imports] / [test-bom-imports] — merged with each member's own imports. Member entries take precedence on a name collision.
  • [repositories] — also inherited; member entries appended.
  • Boolean flags ([java] enablePreview, [spock] enabled) — a member's explicit value wins, including false. A member can set enablePreview = false or [spock] enabled = false to opt out of a flag the workspace turned on.

Members declare dependencies with empty version strings ("") to defer to the inherited BOMs:

app/Curie.toml 
[application]
name      = "app"
version   = "0.1.0"
mainClass = "com.example.App"

[dependencies]
# resolved from the workspace's jackson-bom
"com.fasterxml.jackson.core:jackson-databind" = ""

[workspace-dependencies]
core  = { path = "../core" }
utils = { path = "../utils" }

Topo-sorted builds

Run curie build from the workspace root and Curie computes a topological order over [workspace-dependencies], then builds each member in dependency order. Upstream target/classes directories — not just their JARs — are placed on downstream compile classpaths, so downstream tests don't have to wait for upstream JAR packaging to complete.

$ curie build # from workspace root 
Workspace . build (3 members)

[1/3] utils
  Compile         3 source file(s)
  Tests           ✔ 8 tests successful
[2/3] core
  Compile         5 source file(s)
  Tests           ✔ 12 tests successful
[3/3] app
  Resolve deps    7 JAR(s)
  Compile         4 source file(s)
  Tests           ✔ 7 tests successful
  Done            target/app-0.1.0.jar

Targeted builds

Run curie build from a member directory and Curie still respects topology — it builds the member plus its transitive workspace dependencies, but skips siblings the target doesn't depend on. This is the everyday loop in a large monorepo: edit one package, build only what's affected.

List members

curie list from the root prints the member roster and their declared roles (application vs library):

$ curie list 
Workspace . (3 members)
  app    application  v0.1.0
  core   library      v0.1.0
  utils  library      v0.1.0

Nested workspaces

A workspace member can itself be a workspace. Curie recursively flattens nested workspaces into a single member list, and configuration inheritance cascades through all levels — from the outermost root, through each intermediate workspace, down to every leaf member.

3-level nested workspace 
# root/ — level 0
[workspace]
members = ["core-lib", "services"]

# root/services/ — level 1
[workspace]
members = ["greeter-lib", "apps"]

# root/services/apps/ — level 2
[workspace]
members = ["hello-app"]

Workspace dependencies can cross nesting levels. When curie build runs from the root, all leaf members are visible and built in topo order.

Running from any directory: a command invoked from anywhere inside the tree resolves to the outermost enclosing workspace — so the full inheritance chain applies and cross-level workspace-dependencies resolve. From a leaf member, only that member and its transitive deps build. From an intermediate sub-workspace directory (e.g. services/), Curie builds only that subtree's members plus their transitive deps — for example greeter-lib + hello-app, pulling in core-lib as a dependency, while leaving unrelated root-level siblings untouched.

Duplicate detection: if the same project directory appears more than once (directly or through nesting), Curie errors immediately. This also catches cycles — a nested workspace that references its parent triggers the duplicate check.

curie list shows a focused tree rooted at the outermost workspace, highlighting the current project/workspace with ← current. Nodes outside the current subtree are pruned unless they are workspace dependencies (or their ancestors). Each dependency target shows a reverse required by annotation listing its requirers, with paths relative to the target's parent workspace. curie list --all shows the complete tree including unrelated siblings.

$ curie --project services list # focused on the services sub-workspace 
examples  (workspace)
└─ nested-workspace-demo  (workspace)
   ├─ core-lib  library v0.1.0
   │        (required by: services/greeter-lib, services/apps/hello-app)
   └─ services  (workspace)  ← current
      ├─ greeter-lib  library v0.1.0
      │        (required by: apps/hello-app)
      └─ apps  (workspace)
         └─ hello-app  application v0.1.0

Foreign members

Real workspaces often include projects built by other tools — a legacy Make library, a Rust CLI, a CMake native library, an NPM frontend. Curie workspaces can list those as foreign members. curie build, curie test, and curie clean orchestrate them in dependency order alongside native Curie members.

Foreign projects carry no configuration of their own; everything is declared on the enclosing workspace. A directory listed in [workspace] members without a Curie.toml is auto-detected from marker files; optional [workspace.foreign.<path>] configures it further.

Curie.toml — foreign members 
[workspace]
members = ["greeter-lib", "app", "legacy-lib", "rust-tool", "isolated-app"]

[workspace.foreign.legacy-lib]            # optional; legacy-lib has no Curie.toml → auto-detected
type = "make"                             # optional override
dependencies = ["greeter-lib"]
command = ["make", "jar"]                 # build argv override (no shell)
test-command = ["make", "check"]
clean-command = ["make", "distclean"]
artifacts = ["out/legacy-lib.jar"]        # globs → dependents' classpath
env = { LEGACY_HOME = "/opt/legacy" }

[workspace.foreign.rust-tool]
dependencies = ["legacy-lib"]            # ordering only

[workspace.foreign.isolated-app]          # has Curie.toml → foreign curie member
env = { APP_PROFILE = "ci" }              # built by a separate curie process

Registration rules

  • Every member — Curie or foreign — is listed in members. A [workspace.foreign.X] key where X is not in members is a hard error.
  • A members entry with a Curie.toml and no foreign entry is a native Curie member (built in-process).
  • A members entry without a Curie.toml is auto-detected as foreign from marker files; no markers either → hard error.
  • A foreign entry over a directory that has a Curie.toml makes it a foreign Curie member (type = "curie"): built by spawning the curie binary as a subprocess with the declared env. It gets no workspace inheritance, and if it is itself a workspace it is not flattened — the child process owns it.

Default commands

Commands are executed directly (no shell), with cwd = the member directory. Maven/Gradle prefer ./mvnw / ./gradlew when present. Foreign Curie uses the same binary that is orchestrating (std::env::current_exe()), falling back to curie on PATH.

Toolbuildtestclean
mavenmvn -B packagemvn -B testmvn -B clean
gradlegradle buildgradle testgradle clean
cargocargo buildcargo testcargo clean
makemakemake test*make clean*
cmakecmake -S . -B build then cmake --build buildctest --test-dir build*cmake --build build --target clean*

* Graceful skip when the target/script does not exist applies to default commands only (explicit overrides always run and fail loudly). For make, Curie probes with make -n <target>; for npm/bun/yarn it checks scripts.<name> in package.json; for cmake, default test/clean skip when build/CMakeCache.txt is missing. An override of [] skips explicitly. CMake's default build always configures an out-of-source build/ tree first, then builds it (two direct invocations — no shell).

Artifacts and classpath

Foreign members have no target/classes. Dependents receive only the paths matched by artifacts (plus any transitive contribution). Each pattern must match at least one file after a successful build. Curie members can depend on foreign members via normal [workspace-dependencies] path entries.

Execution semantics

  • cwd = member directory; no shell; env applied to the process.
  • Foreign build commands are always invoked — the foreign tool owns its own staleness.
  • In parallel builds, output is muxed like native members; logs land in <member>/target/<action>.log (Curie creates target/ in foreign dirs for this).

Per-command behavior

CommandBehavior
buildRun build command; expand artifacts → classpath contribution
testBuild first, then run test command (skip rules above)
cleanRun tool clean, then remove Curie's target/ logs
listShows foreign members with tool label, e.g. foreign (make)
fmt / audit / updateFiltered out of workspace fan-out; explicit --project <foreign> → error
run / dev / publish / …Hard error: use the foreign tool directly

Foreign Curie members

When a member has both a Curie.toml and a [workspace.foreign.X] entry, Curie spawns itself as a child process. The child gets the declared env, no parent workspace inheritance, and is not flattened if it is a nested workspace. A CURIE_FOREIGN_DEPTH guard caps pathological recursion. Ordering-only dependencies on the parent do not put parent workspace jars on the child's classpath — declare artifacts if you need that.

Maven sync limitation

Foreign members never appear as Maven <module>s. A Curie member that depends on a foreign member cannot express that edge in a synced pom.xml — set [maven] sync = false on that member or the workspace. Nested workspaces under a syncing root may set [maven] sync = false to opt out of aggregator generation entirely (see examples/foreign-projects-demo, which mixes Make, Maven, Gradle, Cargo, CMake, npm, and foreign-Curie members).

Nested workspaces

Foreign members work inside nested workspaces: the recursive expand processes each level's members + foreign map with the inner path prefix. Inheritance still skips foreign leaves at every level.

Git members (polyrepo)

Workspace members can live in separate Git repositories. Instead of a plain directory name, declare a table with path, git, and an optional branch:

Curie.toml — polyrepo workspace 
[workspace]
members = [
    "local-lib",
    { path = "shared-lib", git = "https://github.com/org/shared-lib.git", branch = "main" },
]

When you run any workspace command (curie build, curie test, curie list, …) and a Git member's destination directory does not exist, Curie clones the repository automatically. If the directory already exists it is used as-is — Curie never overwrites an existing checkout.

This works recursively: if the cloned member is itself a workspace whose Curie.toml references other Git members, those are cloned too.

missingMembers policy

The default behaviour is to clone automatically (missingMembers = "clone"). Set it to "error" to require manual cloning instead — Curie will fail with a copy-pasteable git clone command:

Curie.toml — require manual cloning 
[workspace]
members = [
    "app",
    { path = "shared-lib", git = "https://github.com/org/shared-lib.git", branch = "main" },
]
missingMembers = "error"
$ curie build 
error: workspace member "shared-lib" (from https://github.com/org/shared-lib.git) is missing.
Run the following command from the workspace root:

  git clone https://github.com/org/shared-lib.git --branch main shared-lib
ValueBehaviour
"clone"Clone automatically when the directory is missing (default)
"error"Fail with a manual git clone instruction

Parallel build and test

When a workspace has more than one member to build (or test/clean), Curie runs them in parallel — bounded by --jobs (default: CPU count) and respecting the dependency DAG so no member starts before its upstream dependencies are ready.

Parallel build 
# Build all members across 8 cores.
curie build -j8 --no-docker --no-native

# Run tests in parallel (default: all available cores).
curie test

# Clean everything in parallel.
curie clean -j4

Each member's external-command output (javac, kotlinc, junit) is captured on a PTY, buffered per-member, and written to stdout in contiguous blocks prefixed with the member name — for example string-utils | ✔ isBlank_empty_returns_true(). Raw output (including ANSI color codes) is also saved to target/build.log (or test.log, clean.log) inside each member's directory.

If any member fails, Curie stops dispatching new jobs (fail-early) but lets already-running jobs complete. The final error lists every failed member.

Single-member invocations (curie --project services/greeter-lib build where greeter-lib has no dependencies) keep today's direct output with no prefix overhead.

Parallel formatting

curie fmt at the workspace root fans out across every member in parallel. palantir-java-format is resolved once, then the JAR list is shared across the worker threads so there's no contention on the local cache.
