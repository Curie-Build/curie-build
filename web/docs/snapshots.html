SNAPSHOT dependencies

Maven -SNAPSHOT versions are mutable in-development artifacts. Curie resolves them to a unique timestamped build, then pins that exact version in Curie.lock so subsequent builds are reproducible.

Declaring a SNAPSHOT dependency

Write the base version with a case-sensitive -SNAPSHOT suffix. Point the coordinate at a snapshot repository with repository = "…" when it is not on Maven Central:

Curie.toml 
[[repositories]]
id = "nexus-snapshots"
url = "https://nexus.example/repository/maven-snapshots"

[dependencies]
"com.example:internal-lib" = { version = "1.0-SNAPSHOT", repository = "nexus-snapshots" }

Relative file: repository URLs are resolved against the project root (handy for demos and offline fixtures):

Curie.toml 
[[repositories]]
id = "local-snapshots"
url = "file:local-repo"

How resolution works

  1. Curie fetches the version-level maven-metadata.xml under …/artifact/1.0-SNAPSHOT/.
  2. It picks the newest unique filename version (for example 1.0-20260115.120000-1) from <snapshotVersions>, falling back to <snapshot><timestamp> + <buildNumber>.
  3. The JAR and POM are downloaded under the base directory using that unique name — the same layout Maven uses.
  4. Non-unique layouts (local mvn install style artifact-1.0-SNAPSHOT.jar) still work when no metadata is published.

Curie.lock

Whenever a resolve includes a unique SNAPSHOT, Curie writes Curie.lock next to Curie.toml:

Curie.lock 
# Auto-generated by Curie. Pins unique versions of SNAPSHOT dependencies.
# Run `curie build -U` (or `--update-snapshots`) to refresh.

[snapshots]
"com.example:internal-lib:1.0-SNAPSHOT" = "1.0-20260115.120000-1"

On later builds Curie reads the lock and uses the pinned unique version without re-querying metadata. Commit Curie.lock so every developer and CI run get the same snapshot bits.

Refreshing snapshots (-U)

To pick up a newer deploy of the same base SNAPSHOT:

shell 
curie build -U
# or
curie build --update-snapshots
curie test -U

That ignores existing pins, re-fetches maven-metadata.xml, downloads any new unique artifact, and rewrites Curie.lock. Deleting the lockfile has a similar effect on the next normal build.

Offline builds

With --offline, Curie never hits the network. A locked unique snapshot must already be in ~/.m2/repository; otherwise the build fails. Non-unique local installs (artifact-1.0-SNAPSHOT.jar) also work offline without a lock pin.
